# ADR 001：権限と発注の流れをデータベースで強制する

## 判断

組織と店舗の分離はPostgreSQLの行レベルセキュリティ（RLS）、発注の流れ（状態遷移・役割・店舗・見積の版と期限）はトリガーで強制する。アプリの全リクエストは `asUser()` でトランザクション内に `SET LOCAL ROLE procurement_user` と `app.user_id` / `app.org_id` を設定してから実行する。アプリ側の `can()`（`src/core/workflow.ts`）は同じ規則で画面とメッセージを作るためのもので、権威はDBにある。

金額（見積の明細の金額・税率ごとの対象額と消費税・合計）、版、発行者、発注番号、確定金額はトリガーが決め、アプリのロールにはそれらの列の更新権限がない。監査ログと通知もトリガーが書き、アプリのロールには書き込み権限がない。

## 理由

- 発注の業務で一番高くつく不具合は「他店舗の依頼が見える」「本社の承認なしに発注できる」「金額が書き換わる」。APIの実装漏れ一つで起きる設計にしない。
- 監査ログや通知をアプリが書くと、書き忘れる経路が必ずできる。

## 代償

- ルールがTypeScriptとSQLの二か所にある。片方だけ変えるとメッセージと実際の判定がずれるため、`AGENTS.md` で両方の変更とDBテストを義務づけた。金額の規則は `tests/money.test.ts` が両者を300通りずつ照合する。
- PL/pgSQLの条件式はNULLで「偽」になる。店舗を持たない本社のユーザーが店舗の判定をすり抜けないよう、判定は `coalesce(..., false)` と `IS DISTINCT FROM` で書いている（書いた時点で見つけて直した）。
- PGlite（WASM）と実PostgreSQL 17の両方でテストしている。PGliteは同時に1文しか実行しないため、並行操作は実PostgreSQLのテストでだけ確かめられる。

## 実際に見つかった問題

- 実PostgreSQLのテストで、ローカル用のログインロールが制限ロールの権限を継承し、`SET ROLE` なしでも表を読めた（RLSにより0行だったが、権限としては読めた）。PostgreSQL 16以降は継承が「付与ごと」の設定なので、`GRANT ... WITH INHERIT FALSE` で付与するよう直した。
