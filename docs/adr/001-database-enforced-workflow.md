# ADR 001：権限と依頼の流れをデータベースで強制する

## 判断

会社と拠点の分離、原価をA社に見せないことはPostgreSQLの行レベルセキュリティ（RLS）で、依頼の流れ（状態の変更・役割・拠点・見積書の版と期限）はトリガーで強制する。アプリの全リクエストは `asUser()` で、トランザクションの中で制限ロール `procurement_user` に切り替え、`app.user_id` / `app.org_id` を設定してから実行する。アプリ側の `can()`（`src/core/workflow.ts`）は、同じ規則で画面とメッセージを作るためのもので、決め手はDBにある。

役割は3つ。A社の担当者（`client`、拠点に属する）、B社の担当者（`agent`）、B社の管理者（`admin`）。

A社への見積書は `app.issue_quote` だけが作る。この関数は `SECURITY DEFINER` で、呼んだ人が同じ会社のB社かを関数の中で確かめ、売値・税率ごとの対象額と消費税・合計・版・原価計・利益を計算する。アプリのロールは見積書と原価の表に行を足せない。依頼番号・発注番号・日時・合意の金額もトリガーが決め、アプリのロールにはそれらの列を変える権限がない。監査ログと通知もトリガーが書き、アプリのロールには書く権限がない。

原価・利益・メーカーは、A社が読めない表（`makers`・`maker_quotes`・`quote_costs`）にだけ置く。A社が読む見積書（`quotes`）には売値しかない。

## 理由

- 購買代行の業務で一番高くつく不具合は、「他の拠点の依頼が見える」「A社に原価や仕入れ先が見える」「合意なしに発注できる」「金額が書き換わる」。APIの書き漏れ一つで起きる作りにしない。
- 原価を見せない判定を画面やAPIごとに書くと、新しい画面や通知を足すたびに漏れる経路ができる。表を分けてRLSで閉じれば、どの経路からも読めない。
- 監査ログや通知をアプリが書くと、書き忘れる経路が必ずできる。

## 代償

- 規則がTypeScriptとSQLの二か所にある。片方だけ変えると、画面のメッセージと実際の判定がずれる。そのため `AGENTS.md` で、両方の変更とDBのテストを必ず行う決まりにしている。金額の規則は `tests/money.test.ts` が、税・税込からの換算・利益の載せ方をそれぞれ300通りずつ照合する。
- PL/pgSQL の条件式は NULL のとき「偽」として扱われる。拠点をもたないB社の人が拠点の判定をすり抜けないよう、判定は `coalesce(..., false)` と `IS DISTINCT FROM` で書いている。
- PGlite（WASM）と実PostgreSQL（16・17）の両方でテストしている。PGlite は同時に1文しか実行しないため、同時の操作は実PostgreSQLのテスト（`tests/postgres.test.ts`）で確かめる。

## 実際に見つかった問題

- 実PostgreSQLのテストで、ローカル用のログインロールが制限ロールの権限を継承し、`SET ROLE` なしでも表を読めた（RLSにより0行だったが、権限としては読めた）。PostgreSQL 16 以降は継承が「付与ごと」の設定なので、`GRANT ... WITH INHERIT FALSE` で付与するよう直した。今も `tests/postgres.test.ts` で、ログインロールが `SET ROLE` なしでは何も読めないことを確かめている。
