## RLSの守備範囲

RLSとトリガーは、アプリのコードの誤り（権限の確認の書き忘れ、IDの取り違え）から、拠点の分離・原価の非表示・依頼の流れを守ります。制限ロールとして任意のSQLを実行できる人は、リクエストの文脈（`app.user_id` / `app.org_id`）を自分で設定できます。そのため、DBの接続情報は秘密として管理します。

## 対応範囲と実運用で加えるもの

- **認証**：メールアドレスとパスワードでログインします。SSO・パスワードの再設定・多要素認証は、認証基盤を入れるときに加えます（差し替える境目は `sessionFromToken()`）。
- **ログイン試行の制限**：1つのプロセスのメモリで数えます。複数台で動かすときは、共有の仕組みか前段のプロキシ・WAFで制限します。大量のリクエストへの備えも前段で行います。アカウント単位の制限は、誰の失敗でも5回でそのアカウントを5分止めます。
- **メーカーのサイトの内容**：取り込んだ価格はカタログの参考単価です。見積書の金額は、B社がメーカーの回答から入力した原価をもとにDBが計算します。
- **メールの到達性**：SPF・DKIM・DMARC はSMTPの提供元で設定します。
