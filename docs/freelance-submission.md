# 備品発注ワークフロー — 提出用説明

## 何を解決するか

対象は、複数の店舗を持つ飲食・小売チェーンの本社購買と店舗スタッフです。店舗が消耗品や備品をメールや電話で本社に頼み、本社が仕入先に見積を取り、金額を店舗に確認してから発注する、という流れを想定しています。行き違い（どの版の金額で合意したか分からない、店舗は頼んだつもりで本社は待っていた、発注金額が店舗に伝わっていない）を、状態と合意の記録で防ぎます。

このリポジトリは、仕入先サイトからのカタログ取り込み → 店舗の依頼 → 本社の承認と見積 → 店舗の承諾 → 発注確定と金額の通知までを、権限・監査ログ・通知つきの業務システムとして示す技術デモです。

**実顧客への導入実績、削減時間、契約獲得実績はありません。** 架空の会社と、同梱の架空の仕入先サイトで動作を示します。実在の通販サイトからの取り込みは、サイトによって読めないことを確認しています（[検証記録](verification.md)）。

## 2〜3分のライブデモ（DB・APIキー不要）

1. 手元で `npm run dev` を開き、役割の選択画面を表示する。架空の「株式会社サンプルカフェ」（3店舗と本社）であること、カタログは架空の仕入先サイトから実際と同じ処理で取り込んだものであることを説明する（`/demo-supplier/` でそのサイトを見せる）。
2. **佐藤（渋谷店）** でカタログを開き、コピー用紙と緑茶をカートに入れて依頼する。税込表示の価格が税抜の参考単価に換算され、緑茶は軽減税率8%になっていることを見せる。
3. **山田（本社 購買）** で依頼を開き、単価を直し送料を入れて「承認して見積を送る」。合計は税率ごとに分かれ、DBが計算した値が表示されることを補足する。
4. **佐藤** に戻り、見積を開いて「この見積で発注する」→「発注を確定する」。発注番号と確定金額、本社の承認と店舗の承諾の記録、店舗・本社・仕入先への通知が表示される。「通知」で実際に送る予定のメールを見せる。
5. 時間があれば：**鈴木（横浜店）** で修正依頼の履歴（第1版→修正依頼→第2版）、**田中（管理者）** で「サイトから取り込む」と監査ログ。

## 実装として示せること

- **権限の権威はデータベース**：店舗の分離はRLS、状態遷移・見積の版と期限・金額・採番・監査ログ・通知はトリガー。アプリは全リクエストを制限ロールで実行し、起動時に接続ロールがRLSを迂回できないことを検査する。
- **双方の合意を1文で確定**：店舗が現在の見積を承諾する `UPDATE` の中で、発注・採番・確定金額・通知の記録まで終わる。承諾と再見積の同時実行は実PostgreSQLで検証済み。
- **外部サイトを安全に読む**：SSRF対策（接続時のDNS検査、IP表記の正規化、リダイレクトの再検査、大きさと時間の上限）、robots.txt、画像のコピーと形式判定。
- **日本の実務**：税込表示から税抜への換算、税率ごとの区分と1回の切り捨て、Shift_JISのCSV、発注番号の年ごとの連番。
- **公開リポジトリとしての安全**：[SECURITY.md](../SECURITY.md)、[脅威と対策](security.md)、[公開前のセキュリティ確認](security-publication.md)。

## 導入前に決める条件

| 条件           | このデモ                                             | 実導入前に必要なこと                                        |
| -------------- | ---------------------------------------------------- | ----------------------------------------------------------- |
| 仕入先         | 構造化データを載せたサイト、またはCSV                | 実際の仕入先が読めるかの確認、利用規約の確認、CSVの取り決め |
| 価格           | 取り込み時点の参考価格。発注額は本社の見積で確定     | 契約単価・数量割引の扱い、仕入先からの正式な見積との照合    |
| 承認           | 本社の見積＝承認、店舗の承諾＝合意                   | 金額による承認段階、予算の管理                              |
| 発注           | 発注書をメールで仕入先へ                             | 仕入先のEDI・発注システムとの連携、FAX等の運用              |
| 通知           | SMTPでメール（設定しなければ画面のみ）               | 送信ドメインの認証（SPF・DKIM）、チャットへの通知           |
| 認証           | メールとパスワード。MFA・SSO・パスワードリセットなし | 認証基盤への置き換え（差し替え境界は `sessionFromToken()`） |
| 店舗・メンバー | 設定ファイルから一括作成                             | 画面での追加・異動・退職の扱い                              |
| 運用           | ログイン試行の制限は1プロセスのメモリ内              | 複数台で共有する試行制限、監視、バックアップ、障害対応      |

## レビュー時の再現方法

```sh
npm ci
npm run typecheck && npm test && npm run build
npx playwright install chromium && npm run test:e2e
npm run db:up && RUN_POSTGRES_TESTS=1 npx vitest run tests/postgres.test.ts
```

同じ手順をGitHub ActionsのCIが毎回実行します。

## 作者の実力として説明する際の注意

このプロジェクトはAI支援で実装・検証しています。成果物だけで作者自身の設計・実装力すべてを証明するとは主張しません。次の内容を自分の言葉で説明し、変更を再現できることが信頼につながります。

- 権限と金額をアプリではなくDBで決める理由と、規則がTypeScriptとSQLの二か所にある代償。
- 「双方の合意」をどの時点のどの記録で判定しているか、再見積と承諾がぶつかったときに何が起きるか。
- 指定されたURLを読むときに、なぜ名前解決の答えを接続の時点で検査するのか。
- 通知をoutboxに書いてから送る理由と、「少なくとも1回」の代償。
- 新しい状態（例：検収）を1つ追加し、TypeScript・SQL・テストを揃えられること。

採用や契約の保証ではなく、設計判断と再現可能な検証を材料として提示します。
