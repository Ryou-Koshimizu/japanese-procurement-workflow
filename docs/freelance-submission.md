# 備品発注ワークフロー — 提出用説明

## 何を解決するか

対象は、店舗をもつ会社（A社）と、その会社の什器・備品の調達を代わりに行う購買代行（B社）です。A社の拠点は電話やメールでB社に頼み、B社は聞き直し、メーカーに見積を取り、利益を載せた金額をA社に伝え、合意をもらってから発注します。このやりとりでは、次の行き違いが起きます。

- 依頼に要る情報が足りず、何度も聞き直す
- どちらが返事を待っているのか分からない
- どの版の金額で合意したのか分からない
- A社あての資料に、メーカーの原価や名前が混ざる
- 発注した後の納期がA社に届かない

このリポジトリは、依頼フォーム → アプリの中でのヒアリング → 商品概要の確定 → メーカーの相見積 → 見積書 → A社の合意 → メーカーへの発注 → 納期のお知らせまでを、権限・監査ログ・通知つきの業務システムとして動かします。

架空の会社と、同梱の架空のメーカーのサイトで動作を示すデモです。実在の通販サイトからの取り込みは、サイトによって読めないことを確かめています（[検証記録](verification.md)）。

## 2〜3分のライブデモ（インストール不要）

公開デモ <https://japanese-procurement-workflow.vercel.app>（手元なら `npm run dev`）を開きます。パスワードは全員 `demo-password-2026` です。

| 山田 花子      | B社（みどり購買サポート株式会社）担当者    |

1. **はじめに**：会社・人物・メーカーはすべて架空だと伝えます。さくら備品サプライのカタログは、同梱の架空のサイト（`/demo-supplier/`）から、実運用と同じ処理で取り込んだものです。
2. **佐藤（渋谷店）**：「依頼する」でフォームを送ります。必須の項目を空けると、その項目の横に理由が出ます。
3. **山田（B社）**：依頼を開いて「質問を送る」。**佐藤**に戻って「回答を送る」。山田が残す「B社メモ」は佐藤の画面に出ないことを見せます。
4. **山田**：商品概要を書いて（カタログからも選べます）「商品概要を確定する」。メーカーを2社選んで見積を依頼し、それぞれの「受け取った見積を入力」で原価・在庫・納期の目安を入れます。2社の比較と最安が並びます。
5. **山田**：「原価に率を載せる」を選んで「見積書をA社に送る」。売値・税率ごとの消費税・合計は、DBが計算した値です。
6. **佐藤**：見積書には売値・税・合計だけが出て、原価・利益・メーカー名は出ません。「合意する」を押します。
7. **山田**：「メーカーから直送」を選んで「メーカーに発注する」（発注番号が付きます）。納期を入れて「納期を確定してA社に知らせる」。
8. **佐藤**：「通知」に【納期のお知らせ】が届き、納期と合計が書かれています。
9. 時間があれば：**佐藤**で「レジ回りの消耗品」の依頼を開き、第1版 → 修正依頼 → 第2版の履歴を見せます。**鈴木（梅田店）**で渋谷店の依頼のURLを開くと404です。**田中**で「依頼フォーム」の項目の編集と「監査ログ」を見せます。

## 実装として示せること

- **権限の決め手はデータベース**：拠点の分離と原価の非表示はRLS、状態の変更・見積書の版と期限・金額・採番・監査ログ・通知はトリガーと関数で決めます。アプリは全リクエストを制限ロールで実行し、起動のときに接続ロールがRLSを迂回できないことを確かめます。
- **2つの値段を別の表に**：メーカーの原価と利益はA社が読めない表に、A社への売値は見積書の表に置きます。A社の画面・API・メールには売値・税・合計だけが届きます。
- **合意を1文で記録**：A社が今の見積書に合意する `UPDATE` 1文の中で、依頼が「発注待ち」に進み、合意の金額を見積書から写し、B社への通知を記録します。合意と再見積の同時実行は、実PostgreSQLで確かめています。
- **外部のサイトを安全に読む**：SSRF対策（接続時のDNSの検査、IP表記の正規化、リダイレクトの検査し直し、大きさと時間の上限）、robots.txt、画像のコピーと形式の判定。
- **日本の実務**：税込の掲載価格から税抜への換算、税率ごとの区分と1回の切り捨て、Shift_JIS のCSV、依頼番号と発注番号の年ごとの連番。
- **公開リポジトリとしての安全**：[SECURITY.md](../SECURITY.md)、[脅威と対策](security.md)、[公開前のセキュリティ確認](security-publication.md)。

## 導入前に決める条件

| 条件           | このデモ                                                            | 実運用で加えるもの                                                    |
| -------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------- |
| メーカー       | 登録したメーカーに、見積依頼と発注書をメールで送る                  | 実際のメーカーの連絡先、メールで受けて返す運用の取り決め              |
| カタログ       | 構造化データを載せたメーカーのサイト、またはCSVから取り込む         | 実際のメーカーのサイトが読めるかの確認、利用規約の確認、CSVの取り決め |
| 価格           | 原価はB社がメーカーの回答から入力し、売値は率を載せるか直接入力する | 契約単価・数量割引の扱い、メーカーの正式な見積書との照合              |
| 合意           | 依頼した拠点のA社の担当者が、今の見積書に合意する                   | A社の中での金額による承認の段階、予算の管理                           |
| 発注           | 発注書をメールでメーカーへ（直送かB社経由）                         | メーカーのEDI・発注システムとの連携、FAXなどの運用                    |
| 通知           | SMTPでメール（設定しなければ画面の「通知」だけ）                    | 送信ドメインの認証（SPF・DKIM）、チャットへの通知                     |
| 認証           | メールアドレスとパスワード                                          | 認証基盤への置き換え（差し替える境目は `sessionFromToken()`）         |
| 拠点・メンバー | 設定ファイル（`org.json`）から一括で作る                            | 画面での追加・異動・退職の扱い                                        |
| 運用           | ログイン試行の制限は1つのプロセスのメモリで数える                   | 複数台で共有する試行の制限、監視、バックアップ、障害への対応          |
| 対応範囲       | 依頼から納期のお知らせまで                                          | 請求・支払い・検収、在庫の管理                                        |

## 説明と再現の材料

このプロジェクトはAI支援で実装・検証しています。次の点を、作者の説明と、手元で再現できる変更の材料として示します。

- 権限と金額をアプリではなくDBで決める理由と、規則がTypeScriptとSQLの二か所にある代償。
- 「合意」をどの時点のどの記録で判定しているか。再見積と合意がぶつかったときに何が起きるか。
- 原価・利益・メーカーをA社に返さない仕組み（表の分け方とRLS）。
- 指定されたURLを読むときに、名前解決の答えを接続の時点で検査する理由。
- 通知を outbox に書いてから送る理由と、「少なくとも1回」の代償。
- 新しい状態（例：検収）を1つ足し、TypeScript・SQL・テストを揃える手順。

示すのは、設計の判断と、誰でも同じ手順でたどれる確認です。
