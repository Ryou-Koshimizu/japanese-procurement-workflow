# 公開前のセキュリティ確認

2026-10-16、GitHubで公開する前に、リポジトリの全履歴と公開対象のファイルの点検と、コードの静的なセキュリティレビューを行いました。秘密の値を点検ログに出さない方針で行っています。

## 公開対象の点検

- **秘密情報**：Stripe・AWS・GitHub・Slack・Googleのキー、JWT、秘密鍵の既知パターンを全ファイルに対して検索し、該当なし。パターン検索は未知の形式の秘密を完全に検出する保証ではないため、GitHubのSecret scanningとPush protectionも有効にしています。
- **環境変数**：`.env.example` のSMTPは空欄。`.env*` は `.env.example` 以外をgitignoreで除外。
- **コミットの作者**：全コミットの作者・コミッターがGitHubのnoreplyアドレス。
- **個人情報**：メールアドレスは `example` のドメイン（予約済み）のみ。会社・店舗・人物・仕入先・商品・ブランドはすべて架空。手元のファイルパスの混入なし。
- **実在の仕入先のデータ**：含まない。動作確認で読んだ実在サイトのページは保存していません（[検証記録](verification.md#実在の通販サイトでの確認)）。
- **画像**：架空の仕入先の商品写真は ChatGPT（OpenAIの画像生成）で作ったもので、文字・ロゴ・実在のブランドを入れないよう指示し、1枚ずつ目で確かめています。WebPに書き出す際にメタデータを除き（`cwebp -metadata none`）、EXIF・XMP・ICCのチャンクがないことを確認しました。AIで作った画像であることは README と [ADR 005](adr/005-demo-without-network.md) に明記しています。
- **依存パッケージ**：CIで `npm audit signatures`（レジストリ署名の検証）と、本番依存の高リスク以上の脆弱性で失敗する監査を毎回実行します。メール送信の `nodemailer` は、公開から2週間以上経った版（10.0.13）に固定しています。

## レビューで見つけて直したこと

コードを実行しない静的レビュー（RLS・権限・トリガー・SECURITY DEFINER関数・SSRF・取り込んだデータの扱い・競合）を、実装とは別のエージェントで行いました。主な経路（他店舗の依頼の操作、店舗による見積、本社による承諾、発行後の金額や明細の変更、通知や発注番号の偽造、他人の通知の参照）にすり抜けは見つかりませんでした。次の13点を直し、それぞれ `tests/review-fixes.test.ts` で再発を防いでいます。

| 重さ   | 内容                                                                                                                                                       | 対応                                                                     |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 中〜高 | カートに入れた後で本社が掲載を止めた商品を含むまま、APIを直接呼べば依頼を送れた。DBの判定が店舗のRLSの下で動き、掲載停止の商品が見えないため素通りしていた | 判定をRLSを通さない関数（`app.order_has_unorderable_lines`）に移した     |
| 中     | 取り込みがページ数・時間の上限で止まったり一部のページで失敗したりしても、読めなかった商品をすべて発注不可にしていた                                       | 完全に読めた取り込みでだけ「載らなくなった商品」を判定する               |
| 中     | `<meta` などの閉じないタグを大量に並べた3MBのページで、タグを探す正規表現が二乗の時間になり、サーバーが止まった                                            | `indexOf` による線形の走査に置き換え。属性も1回の走査で読む              |
| 中     | robots.txt の `*` を正規表現の `.*` に変えていたため、`*` を多数含む規則で照合が極端に遅くなった                                                           | 部分ごとの `indexOf` による照合に置き換え                                |
| 中     | 圧縮された応答が途中で切れると、展開側にエラーが伝わらず取り込みが終わらなかった（可能性の指摘。手元のサーバーで再現を確認）                               | `pipeline()` でつなぎ、閉じたら必ず失敗として返す                        |
| 低     | 2月30日のような実在しない日付で500になった                                                                                                                 | 日付を暦として検査し、DBの日付エラーも400にする                          |
| 低     | リクエストを処理するロールが、ログイン用の関数（パスワードハッシュを返す・セッションを作る）を呼べた（アプリの経路からは到達不能）                         | ログインとセッション確認を別のロール `procurement_auth` に分けた         |
| 低     | 数量に空文字や `null` を送ると0とみなされ、カートの明細が消えた                                                                                            | 数値か数字の文字列だけを受け付ける                                       |
| 低     | 500文字を超える商品のキーを切り詰めて保存したため、先頭が同じ別の商品が1つにまとまり得た                                                                   | 長いキーはハッシュを付けて区別する                                       |
| 低     | 同じ商品をもう一度カートに入れても、最初に入れた時の価格のままだった                                                                                       | カートが開いている間はカタログの価格を写し直し、依頼を送る時にも写し直す |
| 低     | プロキシのヘッダーがない構成では全員が同じ「接続元」とみなされ、20回の失敗で全員がログインできなくなった                                                   | 接続元が分からないときはアカウント単位だけで数える                       |
| 低     | IPv4変換アドレス（`::ffff:0:a.b.c.d`）とローカル用NAT64（`64:ff9b:1::/48`）を公開アドレスと判定していた（悪用できる経路は組めなかった）                    | 遮断する範囲に追加                                                       |
| 低     | 依頼一覧の件数を、表示する最新300件から数えていた                                                                                                          | 件数はDBで全件から数える                                                 |

ほかに、実PostgreSQLのテストで、ローカル用のログインロールが制限ロールの権限を継承していた（`SET ROLE` なしで表を読めた。RLSにより0行）ことを見つけ、`GRANT ... WITH INHERIT FALSE` で付与するよう直しています（[ADR 001](adr/001-database-enforced-workflow.md)）。

残っている制約（複数台でのログイン制限の共有、アカウント単位の制限による一時的な締め出し、メールの到達性など）は [脅威と対策の「対象外」](security.md#対象外) に書いています。

## GitHubの設定

Secret scanningとPush protection、Dependabotのアラートとセキュリティ更新、CodeQL（`security-extended`）、プルリクエストでの依存関係の審査、非公開の脆弱性報告、`main` の強制プッシュと削除の禁止。GitHub Actionsは全アクションをコミットSHAで固定し、既定の権限を空にしてジョブごとに最小限を付与、チェックアウトの認証情報を残しません。

## 公開しているサンプル値

`.env.example`、`docker-compose.yml`、`db/local-roles.sql` には、ローカルのPostgreSQL用のユーザー名とパスワード（`*_local_only`）があります。秘密ではなく公開前提の開発用の値で、DBのポートは `127.0.0.1` にだけ公開します。**本番・共有環境では使わないでください。** 公開デモのログイン用パスワードも同じく公開前提です。

## 公開ソースと公開サービスは別

これはコードをGitHubで公開するための確認で、実運用サービスとしての安全性評価ではありません。実データを扱う前に、認証基盤（MFA・SSO・パスワードリセット）、複数台で共有するログイン試行制限、監視とバックアップ、仕入先の利用規約の確認、メールの送信ドメイン認証が別途必要です（[導入前に決める条件](freelance-submission.md#導入前に決める条件)）。
